# Optional Flash Decisions pilot

The personal fork can replace **only the first Flash action** on a recognized
Android Settings homepage with a bounded candidate selection. It does not
replace planning, UI grounding, execution, task completion reporting or Pro.

## Enable and rollback

The default is off. Set `ARTEMIS_FLASH_DECISIONS=1` in the runner process or
Artemis `.env` to opt in; `0` disables it. Reload a long-lived MCP/daemon after
changing its environment. For comparisons use fresh MCP processes with separate
environments and `ARTEMIS_STANDALONE=1`, so concurrent tasks and the daemon's
cached configuration are not modified.

The adapter reads the existing Google provider in `~/.opencodex/config.json`.
It accepts only `authMode=key` and the exact native Google API origin, and sends
the key only to `https://generativelanguage.googleapis.com/v1beta/decisions`.
It does not change billing, keys or OpenCodex routing.

## Execution contract

1. Flash captures its normal initial screenshot and indexed UI list.
2. With no injected guidance, the opt-in adapter recognizes Settings homepage
   title rows. Available candidates are one up/down swipe or opening an existing
   Wi-Fi/Bluetooth title row. Toggles, input, other apps, and later turns are not
   candidates.
3. An exact standalone `Open Wi-Fi settings` / Bluetooth instruction uses a
   local rule. Other supported instructions call `gemini-decision-1`, including
   an `other` candidate. Only the goal and fixed candidate descriptions are sent;
   screenshots, network names and arbitrary UI text are not sent.
4. Accept only a known choice, valid normalized probabilities, confidence and
   selected probability >=0.90, and margin >=0.25. Recheck the foreground package,
   homepage anchors, title identity and bounds before returning the existing
   action tool. The full optional operation has a 3-second deadline.
5. Missing credentials, HTTP errors (including 402/403/429/503), invalid results,
   timeout or page drift return control to the existing Flash model. The adapter
   never retries a charge or executes a second independent device action.
6. Normal Flash observes the result and reports task completion. No synthetic
   completion verdict is generated by the adapter.

Measured API usage is recorded even when a usable answer is later rejected.
Structured `decision/flash_initial_action` traces record outcome and full
optional-path latency; ordinary `llm_usage` traces carry provider token counts.
A local-rule selection uses zero model tokens and never calibrates the transcript
against an unsent full Flash prompt. Count `llm_usage` once, including background
summaries, when comparing session usage. An API timeout can have unknown remote
usage; zero recorded usage is not proof of zero billing.

## Adoption boundary

This is an opt-in pilot. Require correct final UI and exact action count, not
only a model's `completed` report. Compare identical goals from the same initial
page, alternate order, separate API selection from local rules, and report
session duration, first action latency, summary drain, and all measured tokens.

2026-11-12/13 device evidence and the measured rollout decision are documented
in `docs/verification/flash-decisions-2026-11-13.md`. Broader app navigation, multi-step candidate
planning, checkpoint substitution and enabling by default need separate evidence.
